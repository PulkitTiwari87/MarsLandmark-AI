# Data Split Methodology — MarsLandmark-AI

Status: **Implemented and run against the real dataset.**
`src/data/split.py` generates the split; `data/processed/split_manifest.csv`
(git-ignored, regenerate via `python -m src.data.split`) is the persisted
assignment and `reports/split_report.json` is the measured outcome.

## Why a custom split is required

`docs/DATASET.md` confirms this archive (`hirise-map-proj-v3.zip`) ships
**no official train/validation/test split** — only one flat label file
covering all 73,031 images. Any split used by this project must therefore
be constructed here, and the methodology must be documented before any
model is trained, per project rule §0.7 (leakage prevention) and §0.6
(test-set integrity).

## Leakage risk in this dataset

Each of the 10,433 original landmark crops was augmented into 6 additional
images (90°/180°/270° rotation, horizontal flip, vertical flip, brightness
adjustment) — see `docs/DATASET.md`. An augmented image is visually and
semantically almost identical to its original. **A naive random split over
all 73,031 images would very likely place an original in one split and its
own rotated/flipped/brightened sibling in another split** (e.g. original in
train, its horizontal flip in test). That would leak information: the
model could effectively "see" a near-duplicate of a test example during
training, inflating measured test accuracy without reflecting real
generalization.

Filenames encode which crops share a source HiRISE image strip (e.g.
`ESP_011623_2100_RED-0069.jpg` and `ESP_011623_2100_RED-0069-r90.jpg` are
the same underlying landmark). More broadly, crops from the *same* source
strip may depict adjacent or repeated terrain features, so even distinct
crop IDs from one strip are not fully independent.

## Chosen strategy: group split by source HiRISE RED-strip ID

Split at the **source-strip level**, not the image level: every image
(original and every augmented variant, and every distinct crop) whose
filename shares a source RED-strip ID is assigned to exactly one of
train/validation/test. This guarantees:

- No augmented sibling of a training image appears in validation or test.
- No two crops from the same source strip are split across sets.

This was measured as feasible directly from the data: regex-parsing all
73,031 filenames against `{MISSION}_{ORBIT}_{ANGLE}_RED-{crop_id}[-{aug}].jpg`
succeeded for 100% of files with 0 parse failures, yielding 173 group keys
(see `docs/DATASET.md` for the 173-vs-180 discrepancy note, which does not
affect the validity of this grouping).

## Implemented algorithm (`src/data/split.py`)

Two phases, both operating on source-strip groups (never splitting a
group):

1. **Minimum class-coverage pass.** A first attempt using only
   proportional size-balancing (phase 2 below, with no phase 1) was run
   and *measured* to fail: "bright dune" ended up with 0 images in `val`,
   and "swiss cheese" with 0 images in `test` — a real integrity problem,
   not a hypothetical one, since a class absent from a split cannot be
   validated or benchmarked on it. Phase 1 fixes this: for each class, the
   smallest available group containing that class is reserved for `val`,
   then another for `test` (skipped, and reported via
   `classes_missing_per_split`, if too few distinct groups exist for a
   class — this has not occurred on the real dataset).
2. **Proportional-deficit pass.** All remaining groups, largest first, are
   assigned to whichever split is currently furthest below its target
   share: `argmin_s (current_size[s] + group_size) / target_fraction[s]`
   (a standard largest-remainder-style apportionment method).

## Measured result on the real dataset (val=0.15, test=0.15, seed n/a — algorithm is deterministic, no RNG)

From `reports/split_report.json`, generated by
`python -m src.data.split --data-dir data/raw`:

| Split | Images | Fraction (target 0.70/0.15/0.15) | Source groups | Classes missing |
|---|---:|---:|---:|---|
| train | 51,128 | 0.7001 | 108 | none |
| val | 10,955 | 0.1500 | 33 | none |
| test | 10,948 | 0.1499 | 32 | none |

Size ratios land within 0.01 percentage points of target; every class is
represented in every split. Per-class counts per split are in
`reports/split_report.json` (`per_split_class_distribution`) — some rare
classes (e.g. impact ejecta: 91/119/21 in train/val/test) have very few
val/test examples, which the per-class metrics reported in later phases
must account for (wide confidence intervals on those classes' metrics,
not treated as equally reliable as "other"/"crater").

## What is still NOT decided

- **Stratification beyond "at least one group."** The algorithm guarantees
  non-zero class coverage per split, not proportional class balance. This
  is a measured limitation, not a gap to silently work around.
- **Whether 70/15/15 is the final ratio used for training.** These are the
  values run above; Phase 05/06 may revisit if e.g. the val set proves too
  small for reliable model selection on rare classes — any change will be
  re-run and re-measured here, not assumed.
